# 容易再犯的错误

每次给推荐答案前对照一遍。

## 关于事实

| 容易犯的错 | 应该怎么做 |
| --- | --- |
| 推荐答案凭印象写成一套“一般会这么做”的计划，产品其实没这样设计 | 先查代码和文档，每个做法都对上文件；查不到就说没找到，标成计划或问用户 |
| 说“没做过对比”，其实决策记录或测试分支里有完整的对比实验 | 开局先列证据地图；用户说“我记得做过”时认真找 |
| 用户想说“假设这个评测我已经做过” | 不编结果。口径可以按“做过”写，结果处留〔〕占位，并记进待办 |
| 不确定是谁判的（真人还是模型），写成了“人工复核” | 不确定的事实不写成确定说法；模型判的就写模型判的 |
| 外部报告里的说法（“最常见的品类”）直接沿用 | 逐条查出处；只部分成立就降级为“之一” |
| 用户的口头说法和代码设计冲突 | 以产品实际设计为准，帮用户把设计讲成策略 |
| 设计理由是自己推断的，却写得像有记录 | 依据里标明“按设计推断，仓库里没有写明” |
| 只讲门槛怎么定，没拿历史数据回查 | 把门槛套到全部历史数据上看误判；发现问题告诉用户，修完再写 |
| 产品承诺和实现不符（页面说“已记录”，其实没存）没被发现 | 讲指标和反馈闭环前，先核对数据真的落库了 |

## 关于读题

| 容易犯的错 | 应该怎么做 |
| --- | --- |
| 题目写成“你这个是真的吗”“这个数字准不准” | 面试官只问怎么做的、为什么、怎么取舍 |
| 题目以源码细节为前提（“为什么接这家模型”） | 面试官看不到源码；简历或口头没提到的实现细节不出题 |
| 题目写成“为什么这个值得写进简历” | 口吻是“我注意到你有 X，你是怎么做到的？怎么确信……？” |
| 取舍题是自造的（“为什么回测要赢过基线”这种没有产品取舍的点） | 选面试官真会问的取舍，例如“为什么不用更复杂的模型” |
| 用户把解释方法和预测模型混为一谈，顺着错误前提出题 | 先用一两句温和地澄清两者关系，再把问题接到真正的取舍上 |
| 把“价格准不准”答成“数据从哪来” | 底层问的是“Agent 会不会编东西给用户”，先答这个 |
| 把 ROI 理解成成本 | ROI 是业务收益：多带来多少收入、怎么证明是产品带来的 |
| 降级题讲成限流、熔断这些工程操作 | 这题考原则：总原则 + 分层降级 + 线上问题落到哪一层 |
| 和前面某节重复的题又出一遍 | 已覆盖的内容不再单独出题，换简历上还没问到的句子 |

## 关于写法

| 容易犯的错 | 应该怎么做 |
| --- | --- |
| 说“靠一份约定 / 规范来保证” | 说成具体技术：脚本按什么规则匹配、程序校验什么、不过了退到哪 |
| 口头版结构化太强、短句碎片多 | 写成平常说话的整句；结构留给卡片细节 |
| 根因写成“根子在意图没理清” | 用完整的人话：“根因在于 Agent 没有准确识别用户的意图” |
| 面试官不熟的名词直接抛出来 | 一句大白话说清是什么，深一层的原理放进追问 |
| 评测罗列“几条人判、几条机判” | 每个评测动作配一句理由 |
| 拿大厂文章当标准写进回答 | 外部材料只用来自查思路；回答只讲自己产品的约束和理由 |
| 指标只用产品内部叫法 | 对上行业标准名和公式，说清分母换成了什么 |
| bad case 只讲一个零散的例子 | 按四段式：分类和成因 → 每类一例 → 解法 → 结果影响 |
| 价值讲“提效”“省时”，没有数据也报数字 | 价值落到收入公式和传导链；没数据就标〔缺〕，讲验证计划 |
| 开场埋“我没有用户”这种钩子 | 不主动亮短板做钩子；被问到时如实说 |
| 修了产品问题，卡片前面几节还是旧说法 | 修完把受影响的各节一起更新，前后口径一致 |

## 关于节奏

- 一次只问一题；用户说“先暂停”就停，说“继续”再接着问。
- 用户说“定稿”就立刻写进卡片文件；改动先给用户看，再写入。
- 用户只说“还要改”却没说改哪里时，列出几个最可能的问题让他选，并给出你的推荐。
- 用户对题目提出质疑时，可以反驳，但要给出更合理的版本，并说明同领域里通常怎么做。
