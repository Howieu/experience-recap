# 好答案与坏答案对照（脱敏示例）

下面的示例产品是虚构的：一个给内容运营团队用的数据分析 Agent，每周找出表现异常的栏目，解释原因，支持对话追问。数字一律用〔〕占位。照搬的是答案的结构和判断方式，不是内容；真实卡片里的每个事实仍要从用户自己的代码和文档里查。

## 目录

1. 出题：好题目和坏题目
2. “你是怎么做到的”：讲机制，不讲“靠约定”
3. “为什么不用另一种做法”：讲清边界
4. 复杂度取舍题，带一个面试官不熟的名词
5. bad case：四段式
6. 业务价值：传导链和归因

## 1. 出题：好题目和坏题目

| 坏题目 | 问题在哪 | 好题目 |
| --- | --- | --- |
| “你简历说接入新数据源只需一份配置，这是真的吗？” | 面试官不质疑真假 | “我注意到你说接入新数据源只需一份配置，具体是怎么做的？为什么这样设计？” |
| “你说的〔N〕% 这个数准不准？” | 面试官不问准不准，只问怎么来的 | “这个〔N〕% 是怎么算出来的？和什么比？” |
| “为什么接的是某某模型？” | 面试官看不到源码，简历也没写 | 跳过，除非简历或回答里提到了模型 |
| “为什么结论一致这件事值得写进简历？” | 口吻不对 | “我注意到你有结论一致这个特性，你是怎么做到的？怎么确信每次都一样？” |
| “为什么回测要赢过基线才用模型？” | 没有真正的产品取舍 | “为什么用这么简单的模型，不用更复杂的？” |

## 2. “你是怎么做到的”：讲机制，不讲“靠约定”

**题目：** 我注意到你说同样的数据两次运行结论一致，你是怎么做到的？

**坏答案：**

> 我们和模型约定好了输出格式，温度设成 0，所以结论比较稳定。

问题：“约定”和“温度为 0”都不能保证结论一致，被追问一句就露底；没讲为什么这件事重要，也没讲怎么验证。

**好答案（口头版）：**

> 对 Agent 来说这并不理所当然：同一个问题问两次，模型可能换一个角度，点名另一个“最差”的栏目。运营拿报告去开会，会后重跑一次结论变了，这份报告就没人信了；回归测试也分不清是代码改坏了，还是模型这次发挥不一样。
>
> 我的做法是把“下什么结论”交给程序，模型只改措辞。异常按影响大小排序、最差的栏目是哪个，都由程序按固定规则选；遇到并列，按固定顺序取。模型改写的文字要过校验，不过就用程序生成的初稿。
>
> 每次改完都跑 AA 测试，也就是同样的输入跑两次，比较结论。有一次就发现几个栏目指标并列，两次点名了不同的“最差”。原因是并列没有固定规则，几乎没有流量的栏目也参与了评比。修法是并列按名称取，占比不到〔阈值〕的栏目不参与，并补了回归测试。

**为什么好：** 机制具体到“谁选结论、并列怎么办、不过校验退到哪”；讲了为什么重要；用 AA 测试和一个真实 bad case 证明它成立；不完美之处（措辞仍可能不同）留给追问。

## 3. “为什么不用另一种做法”：讲清边界

**题目：** 指标口径为什么写成配置文件，不直接写成一个 skill 让模型去读？

**坏答案：**

> skill 不够稳定，我们用配置文件更规范。

**好答案（口头版）：**

> 区别在于谁来读、谁来执行。skill 写给模型读，模型读完自己决定怎么查、怎么算，口径能不能执行到位要看模型照不照做。配置文件写给程序读：字段校验、生成查询、把用户说的“短视频”对到数据里真实的栏目名，都由程序按这个文件执行，模型只能在程序给的选项里挑。
>
> 我选程序执行，是因为口径错了数字照样像模像样，业务看不出来。这类错了没人发现的东西必须强制执行。流程知识，比如先看哪个指标、周报怎么写，模型确实需要读，我放在提示里。两者不冲突：用户本来在用通用 Agent，也可以写一个 skill 调用这里的工具，口径仍由程序守。

**为什么好：** 先承认对方方案的合理之处，再讲清判断标准（谁读、谁执行、错了怎么发现），给出两者各自适合放什么。

## 4. 复杂度取舍题，带一个面试官不熟的名词

**题目：** 预测用的什么模型？为什么不用更复杂的？

**坏答案：**

> 我们用 SHAP，所以没用 XGBoost。

问题：把解释方法和预测模型混为一谈；名词抛出来没解释；没有讲取舍。

**好答案（口头版）：**

> 预测用的是一个树模型，没用深度学习或时序大模型，原因有三个。第一，数据量小：只有〔N〕条序列，每条〔M〕周左右，模型越复杂越容易把噪声当规律，事实上在粗粒度上连它都赢不过“近几周平均”。第二，业务要能看懂一个预测数是怎么来的，树模型可以把每次预测精确拆开。第三，同样输入结果要一样，普通 CPU 就能跑。
>
> 模型没把握时就不用它：每个范围先用过去半年回测，比简单平均准才用模型，否则用平均值并写明来源。
>
> 拆解用的是 SHAP，它把一次预测拆成每个因素加了多少、减了多少，加起来正好等于预测值。它说明的是模型依赖了什么，不代表业务原因。

**追问准备：** “SHAP 是什么”给深一层的原理（来自博弈论的公平分配）；“深度学习不是更好吗”承认没有实测，只是判断，并说明数据量变大后会放进同一套回测里比。

**为什么好：** 先澄清概念，再把题目接到真正的取舍上；名词一句话讲清；没测过的结论按判断讲。

## 5. bad case：四段式

**题目：** 讲讲你做这个项目时遇到的 bad case。

**坏答案：**

> 有一次模型把一个下滑的栏目说成了增长，我改了提示词，后来就好了。

问题：零散的单个例子；“改提示词”不能保证不再犯；没有结果。

**好答案（口头版）：**

> 我遇到的 bad case 主要分三类。
>
> 第一类，数字对，结论说错了。原因是校验最初只检查数字是否出自工具结果，不检查意思。比如总结写“本周强于月累计”，其实是弱于。解法是校验从“核数字”扩展到“核意思”：方向要和每个比较基准一致，数字要跟着正确的名称；不过校验先修正一次，再不过退回规则文字。结果是同一批〔N〕道题复测，有语义问题的从〔a〕道降到〔b〕道〔离线，判分方式〕。
>
> 第二类，规则的基准选错了。原因是门槛按全局设计，没跟着用户当前看的范围走。比如只看一个小栏目组时，影响很大的异常因为没到全局门槛被滤掉。解法是门槛按查看范围算。结果是〔该视角下报出了这条，全局结果不变〕。
>
> 第三类，数据本身不完整或不稳定。原因是数据会晚到、有些对象几乎没有量。比如最新一周数据只入了一半，报告却当它是本周。解法是明显没入齐就退一周并写明原因，并参考去年同期区分季节性低谷。结果是〔AA 测试结论两次一致；历史回查无误判〕。
>
> 每次修复都写进了回归测试。

**为什么好：** 先分类再举例，每类都有原因、解法和带口径的结果；能接住“为什么不改提示词”的追问。

## 6. 业务价值：传导链和归因

**题目：** 这个产品能带来什么业务价值？怎么证明是它带来的？

**坏答案：**

> 能提效〔N〕%，运营不用再手动拉数了。

问题：没有数据来源；“提效”落不到收入上；没有归因方法。

**好答案（口头版）：**

> 价值分两层。第一层是把问题早一点找出来：产品每周把偏离预期最大的栏目按影响排出来，运营早一周发现、早一周调整，流量损失就能追回一些。链路是：找出异常 → 运营标“要处理” → 调整 → 被标记的栏目回到预期 → 追回的量。每条异常都写了“差多少”，所以追回多少能算。第二层是省下的复盘时间，没有数据，我不报数字。
>
> 证明是产品带来的，不能拿“标了要处理”和“没标”的比，运营本来就会挑严重的处理，会高估效果。应该随机留一部分团队暂时不看，比较两组回到预期的速度。目前没有真实用户，这条链上的线上数据都是缺的。

**为什么好：** 价值落到可计算的量；每个环节标明有没有数据；归因方法能防住选择偏差；不报没有依据的数字。
