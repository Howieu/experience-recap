# 卡片文件模板

文件名：`<经历名>-经历卡片.md`。开头一句写事实依据，然后每节一个模块。不写改动说明和来龙去脉，这些放进给用户的回复或待办记录。

```markdown
# <经历名> · 经历卡片

事实依据：<代码仓库 / 决策记录 / 测试分支 / 本人口述 / 已投简历>。每节先是面试时的口头版，再是被追问时用的细节。

## 一、<面试官的问法，例如：结论两次运行一致是怎么做到的>

### 口头版（约 60 秒）

> <平常说话的整句，40–90 秒能说完：先讲机制，再讲为什么这样设计，最后讲怎么确信它成立>

### 取舍

| 方案 | 好处 | 为什么没选，或代价 |
| --- | --- | --- |
| <否决的方案 A> | … | … |
| <采用的方案>（采用） | … | <代价> |

### 追问：<面试官真会问的追问>

> <回答>

### 不完美

- <没校准的门槛、没做的对比、只是判断没有实测的结论>

依据：<文件路径、提交、测试名>。<按设计推断的理由在这里标明。>

## 二、……
```

## 细节里常用的表格

- Agent 放在哪些环节：环节 / Agent 做什么 / 为什么放这里 / 怎么兜底
- 核心策略：策略 / 为什么做 / 怎么定的 / 现状
- 分层降级：哪一层出问题 / 退到哪里 / 用户看到什么 / 承诺变没变
- 价值传导链：环节 / 指标 / 现在的数据〔线上 / 离线 / 估算 / 缺〕
- bad case 分类：类别 / 原因 / 例子 / 解法 / 结果〔口径〕
- bad case 逐条：时间 / 发现 / 怎么发现 / 修法 / 验证
- 对比测试：配置 / 关键指标若干列
- 四层指标：层 / 指标 / 口径 / 现在的数据

## 待补的写法

结果还没有时写成：`结果是〔填完后补：……〕`，同时记进待办，写清去哪里补、补完怎么算。
